# Канбан — мини-задачник

Канбан-доска с колонками «Новая», «В работе», «Готово»: создание, просмотр, редактирование
и удаление задач, перетаскивание между колонками и внутри колонки, данные в PostgreSQL
через REST API. Работает на компьютере и телефоне.

**Демо:** https://kanban-web-zsuj.onrender.com · API и Swagger:
https://kanban-api-mzfa.onrender.com/api/docs
(бесплатный тариф Render: после простоя первый запрос может занять до минуты)

[![CI](https://github.com/KuliyevMerdan/kanban-test-task/actions/workflows/ci.yml/badge.svg)](https://github.com/KuliyevMerdan/kanban-test-task/actions/workflows/ci.yml)

**Стек:** TypeScript · Next.js 16 + React 19 + Material UI 9 · NestJS 11 + TypeORM ·
PostgreSQL 17 · Socket.IO · Docker · GitHub Actions.

## Возможности

| Обязательное по ТЗ                        | Как сделано                                                                                       |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Три колонки                               | «Новая», «В работе», «Готово» со счётчиками                                                       |
| Создание: название, описание, приоритет   | Диалог с валидацией (та же zod-схема, что и на сервере); «+» в колонке создаёт задачу в ней       |
| Просмотр, редактирование, удаление        | Клик по карточке открывает задачу; меню «⋮» на карточке                                           |
| Перемещение между колонками               | Drag & drop (мышь, долгое нажатие на телефоне, клавиатура), меню «Переместить в…», поле «Колонка» |
| Сохранение после перезагрузки             | PostgreSQL через REST API, порядок карточек тоже хранится                                         |
| Удобно на компьютере и телефоне           | Три колонки на десктопе; на телефоне — вкладки, кнопка «+», полноэкранный диалог                  |
| Состояния загрузки, ошибок и пустой доски | Скелетон, «Сервер просыпается…», ошибка с «Повторить», пустая доска и пустая колонка              |

**Улучшения** (подробнее — [ниже](#улучшения)): отмена удаления, поиск и фильтр по приоритету,
обновление доски в реальном времени.

## Быстрый старт (Docker)

Нужен только Docker.

```bash
docker compose up --build
```

- Приложение: http://localhost:3000
- API: http://localhost:4000/api, Swagger: http://localhost:4000/api/docs

Миграции применяются автоматически при старте API. Postgres публикуется на порт **5433**
(5432 часто занят локальной установкой; меняется переменной `DB_PORT`).

## Локальная разработка

Нужны Node.js 24 (`.nvmrc`), pnpm 10 (`corepack enable`) и Docker для базы.

```bash
nvm use
corepack enable
pnpm install
cp apps/api/.env.example apps/api/.env
pnpm db:up        # Postgres в Docker (+ база kanban_test для e2e)
pnpm db:migrate   # применить миграции
pnpm dev          # API :4000 и web :3000 в режиме watch
```

`apps/web/.env.example` можно не копировать: по умолчанию фронт ходит на `http://localhost:4000/api`.

### Миграции

Схема меняется только миграциями (`synchronize: false`), они лежат в
[`apps/api/src/database/migrations`](apps/api/src/database/migrations).

```bash
# после изменения entity: сгенерировать миграцию и зарегистрировать её в migrations/index.ts
pnpm --filter @kanban/api migration:generate src/database/migrations/<Name>
pnpm db:migrate
pnpm --filter @kanban/api migration:revert   # откатить последнюю
```

E2E-тест проверяет, что миграции синхронны с entity.

## Тесты

| Уровень      | Что проверяется                                                                                                                         |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| Unit (API)   | генератор ключей порядка (крайние случаи, рандомизированный тест с seed); `TasksService`: CRUD, перемещения, 400/404/409, Undo, события |
| E2E (API)    | HTTP → Nest → Postgres: сценарии API, формат ошибок, контракт ответов, `COLLATE "C"`, миграции; realtime настоящим Socket.IO-клиентом   |
| Unit (фронт) | оптимистичные изменения кэша, логика drag & drop, фильтр и его хранение в URL                                                           |

Всего 99 тестов. Чтобы убедиться, что тесты что-то ловят, в код вручную вносились ошибки
(мутационная проверка) — подробности в [docs/AI.md](docs/AI.md). UI-компоненты проверены
вручную в браузере (desktop, 375 px, светлая и тёмная тема); автотестов UI нет.

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) на каждый push и PR: lint, формат,
типы, unit, e2e на сервисном Postgres, сборка, сборка Docker-образов.

## API

| Метод    | Путь                     | Описание                                                                      |
| -------- | ------------------------ | ----------------------------------------------------------------------------- |
| `GET`    | `/api/tasks`             | Все задачи доски по колонкам и порядку                                        |
| `GET`    | `/api/tasks/:id`         | Одна задача                                                                   |
| `POST`   | `/api/tasks`             | Создать (в конец колонки)                                                     |
| `PATCH`  | `/api/tasks/:id`         | Изменить название, описание, приоритет                                        |
| `PATCH`  | `/api/tasks/:id/move`    | `{ status, afterId }`: `afterId: null` — в начало, без поля — в конец колонки |
| `DELETE` | `/api/tasks/:id`         | Удалить (мягко, можно отменить)                                               |
| `POST`   | `/api/tasks/:id/restore` | Отменить удаление                                                             |
| `GET`    | `/api/health`            | Проверка API и базы                                                           |

Ошибки всегда в формате `{ statusCode, error, message, details? }`. После каждого изменения
сервер рассылает по Socket.IO событие `tasks:changed` `{ type, taskId }`.

## Деплой на Render

В репозитории есть [render.yaml](render.yaml) (Blueprint): API и фронт как Docker-сервисы
(те же образы, что в `docker compose`) и Postgres. Всё на бесплатном тарифе.

1. Запушить репозиторий на GitHub.
2. Render → **New → Blueprint** → выбрать репозиторий.
3. Render попросит значения двух переменных. Адреса сервисов обычно имеют вид
   `https://<имя-сервиса>.onrender.com`:
   - `CORS_ORIGIN` (kanban-api) — адрес фронта, например `https://kanban-web.onrender.com`;
   - `NEXT_PUBLIC_API_URL` (kanban-web) — адрес API с `/api`, например
     `https://kanban-api.onrender.com/api`.
4. После создания сверить реальные адреса сервисов в дашборде. Если Render добавил к имени
   суффикс — исправить обе переменные и сделать **Manual Deploy** фронта
   (`NEXT_PUBLIC_API_URL` встраивается в сборку).

Особенности бесплатного тарифа: сервисы засыпают без запросов, первый запрос может занять
до минуты (фронт показывает «Сервер просыпается…» и повторяет запросы); у бесплатной базы
ограниченный срок жизни — см. условия Render.

## Решения

Подробно, с причинами и альтернативами, — в [docs/decisions.md](docs/decisions.md). Кратко:

- **Монорепо (pnpm workspaces)** с общим пакетом `@kanban/shared`: одна zod-схема валидирует
  запросы в API, формы на фронте и описывает Swagger — контракт не разъезжается.
- **Порядок карточек — fractional indexing**: у задачи строковый ключ позиции, перемещение
  меняет одну строку в БД. Колонка `position` с `COLLATE "C"`, иначе Postgres сортировал бы
  ключи не так, как JS (найдено тестом; поэтому образ Postgres — Debian, а не alpine).
- **Перемещение по якорю** `afterId`, а не по индексу: работает на отфильтрованной доске;
  если якорь устарел — `409`, клиент откатывает изменение и перезагружает доску.
- **Оптимистичные обновления** (TanStack Query): перемещение и удаление видны сразу,
  при ошибке откатываются.
- **Слои API**: controller → service → repository, доменная логика порядка — чистые функции.
- Версии: NestJS 11, а не 12 (12-я — ESM-only, это усложнило бы Jest); TypeScript 5.9
  (TS 7 пока не поддерживается typescript-eslint).

## Ограничения

- Нет авторизации и пользователей; одна общая доска; колонки фиксированы (enum в БД).
- Одновременное редактирование одной задачи — «последняя запись побеждает».
- Два одновременных перемещения в одно место могут получить одинаковый ключ — порядок
  остаётся детерминированным (по `id`), но не идеальным.
- Мягко удалённые задачи не вычищаются из таблицы.
- Realtime-события получают все клиенты; для нескольких инстансов API нужен Redis-адаптер.
- Нет автотестов UI (Playwright) — следующий шаг.

## Улучшения

В ТЗ просили предложить одно улучшение; реализованы три небольших:

- **Отмена удаления.** Задача удаляется сразу, без диалога «Вы уверены?», а в уведомлении
  6 секунд доступна кнопка «Отменить» — задача возвращается на прежнее место. Быстрее в
  обычном случае и надёжнее при ошибке, чем подтверждение.
- **Поиск и фильтр по приоритету.** По названию и описанию, без учёта регистра; состояние
  хранится в URL — переживает перезагрузку и им можно поделиться.
- **Обновления в реальном времени.** Изменения из другой вкладки или с другого устройства
  появляются без перезагрузки; в шапке — индикатор связи.

## Использование AI

Код писался поэтапно с AI-ассистентом (Claude Code); каждый этап я ревьюил перед следующим.
AI использовался для каркаса, реализации, тестов и поиска ошибок. Проверка не сводилась к
«запустилось»: версии библиотек сверялись с реестром npm, а не с памятью модели; результат
в браузере сверялся с данными на сервере; в код намеренно вносились ошибки, чтобы убедиться,
что тесты их ловят. Найденные так проблемы (рост ключей порядка, сортировка в alpine-Postgres,
гонка в поле поиска и др.) и как они исправлены — в [docs/AI.md](docs/AI.md).
