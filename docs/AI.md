# Использование AI

Работа шла поэтапно: AI-ассистент (Claude Code) писал код этапа, я ревьюил каждый этап
перед переходом к следующему. Ниже — где AI помог и как проверялся результат.

## Этап 0 — каркас монорепо

**Что сделал AI:** структура монорепо, конфиги TypeScript/ESLint/Prettier, docker-compose
с Postgres, минимальные приложения Nest и Next.

**Как проверялось:**

- Версии не брались «из памяти модели»: перед выбором проверены актуальные версии и
  `peerDependencies` в npm-реестре. Так обнаружилось, что NestJS 12 стал ESM-only, а
  TypeScript 7 не поддерживается `typescript-eslint` — выбор и причины записаны в
  [decisions.md](./decisions.md).
- `pnpm typecheck`, `pnpm lint`, `pnpm build` проходят.
- API поднимается, `GET /api/health` отвечает; Next-страница рендерится с MUI и
  импортом из `@kanban/shared`; Postgres в docker-compose проходит healthcheck.

## Этап 1 — API

**Что сделал AI:** контракт в `@kanban/shared`, TypeORM-entity и миграция, модуль Tasks
(repository / service / controller), fractional indexing, фильтр ошибок, Swagger.

**Как проверялось и что нашлось:**

- **Миграция:** после применения повторный `migration:generate` не находит расхождений
  между entity и схемой; `revert` → `run` проходит; в `\d tasks` видно `COLLATE "C"`
  у `position`. Первая сгенерированная миграция использовала `uuid_generate_v4()`,
  требующую расширения `uuid-ossp`, — переключено на встроенный `gen_random_uuid()`.
- **Сценарии API** (23 проверки скриптом): CRUD, перемещения в начало / середину / конец /
  пустую колонку, 400 на невалидные данные, кривой JSON и не-UUID, 404, 409 на устаревший
  якорь, формат ошибок, наличие DTO в Swagger, 503 из health при остановленной БД.
- **Фаззинг генератора ключей** (тысячи случайных вставок) подтвердил корректность порядка,
  но **выявил проблему**: первая версия алгоритма при добавлении в конец растила ключ
  линейно — 200 символов после 1000 новых задач. Исправлено минимальным шагом на краях
  (33 символа), фазз прогнан повторно. Этот случай войдёт в unit-тесты.
- Порт 5432 оказался занят локальным Postgres, и CLI молча подключался не к той базе —
  docker-контейнер переведён на 5433.

## Этап 2 — тесты бэка

**Что сделал AI:** Jest + ts-jest; unit-тесты генератора ключей и `TasksService`
(на in-memory репозитории с семантикой SQL-запросов); e2e-тесты API на отдельной базе
`kanban_test` со схемой, построенной реальными миграциями.

**Как проверялось, что тесты что-то ловят:**

- **Мутационная проверка вручную.** В сервис по очереди вносились ошибки (не обновлять
  статус, не проверять колонку якоря, не превращать пустое описание в `null`, разрешить
  «после самой себя») — каждую ловит хотя бы один тест. Две мутации (не исключать
  перемещаемую задачу из поиска соседей) тесты не ловят, и это верно: поведение от них
  не меняется — такие мутанты эквивалентны.
- Тест «миграции синхронны с entity» падает, если изменить entity без миграции.
- Предохранитель e2e отказывается запускаться на базе, имя которой не оканчивается на `_test`
  (тесты удаляют схему).
- **Находка:** тест на `COLLATE "C"` проходил и без него. Причина — образ
  `postgres:17-alpine`: в musl libc `en_US.utf8` сортирует как `C`, поэтому локально
  проблема не воспроизводилась бы, а на Render (Debian/glibc) порядок карточек сломался бы
  только в проде. Образ заменён на `postgres:17` — теперь тест без `COLLATE "C"` падает.
- Рандомизированный тест порядка использует ГПСЧ с фиксированным seed: падение
  воспроизводимо, тест не «мигает».

## Этап 3 — фронтенд

**Что сделал AI:** доска на MUI + dnd-kit, React Query с оптимистичными обновлениями,
диалог задачи на react-hook-form с общей zod-схемой, состояния загрузки / ошибок / пустой
доски, мобильная раскладка, unit-тесты чистой логики (Vitest).

**Как проверялось:**

- Ручной прогон в браузере против реального API с проверкой результата **на сервере**
  (`GET /api/tasks`), а не только по картинке: создание через форму, перенос между
  колонками и внутри колонки мышью, перемещение через меню, редактирование со сменой
  колонки, удаление с подтверждением.
- Состояния: остановленный API → скелетон с подсказкой «Сервер просыпается» → после
  повторов ошибка «Нет соединения с сервером» → API поднят → «Повторить» загружает доску.
- Телефон (375 px): вкладки, кнопка «+» создаёт задачу в открытой колонке,
  полноэкранный диалог. Найдено и исправлено: подписи вкладок переносились на две строки.
- Светлая и тёмная тема; в консоли браузера нет ошибок React / гидратации.
- Версии API библиотек сверялись с установленными пакетами, а не с памятью модели:
  в MUI 9 иконка называется `DeleteOutlined` (а не `DeleteOutline`), что поймал `tsc`.

## Этап 4 — улучшения (Undo, поиск/фильтр, realtime)

**Что сделал AI:** мягкое удаление с миграцией и `restore`, Undo в snackbar, фильтр в URL,
WebSocket-шлюз и подписка на клиенте, тесты.

**Как проверялось и что нашлось:**

- Unit: восстановление на прежнее место, идемпотентность, скрытие удалённых задач из
  чтения и перемещения; публикация событий на каждое изменение и их отсутствие при ошибке.
- E2E: `restore` через HTTP; отдельный тест поднимает приложение на порту и слушает его
  настоящим Socket.IO-клиентом. Мутация (рассылка отключена) — тест падает.
- Браузер: задача, созданная через `curl`, появляется на открытой доске без перезагрузки;
  поиск и фильтр меняют URL и переживают перезагрузку; удаление → «Отменить» возвращает
  задачу между теми же соседями (сверено с сервером); пустой результат фильтра.
- **Найдено при ревью собственного кода:** первая версия синхронизации поля поиска с URL
  теряла символы при быстром вводе — запоздавшее «эхо» нашего же обновления URL
  перезаписывало поле. Вторая версия (через `ref` во время рендера) нарушала правила
  React Compiler. Итог — состояние «последнее значение URL» + «последнее отправленное»:
  поле синхронизируется только при внешнем изменении («Сбросить», «Назад»).
- `@nestjs/event-emitter` не использован: актуальная версия 12.x — ESM-only (проверено по
  `"type": "module"` в реестре), а API собран в CommonJS; шина событий — 10 строк на RxJS,
  который уже есть в зависимостях.
