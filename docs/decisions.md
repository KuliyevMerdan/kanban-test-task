# Технические решения

Короткий журнал решений: что выбрали, почему и чем пожертвовали.

## 1. Монорепо на pnpm workspaces

`apps/api` (NestJS), `apps/web` (Next.js), `packages/shared` (общий контракт API).
Один `clone`, общие конфиги TypeScript/ESLint/Prettier, атомарные изменения «бэк + фронт» в одном PR.
Turborepo не используем: для двух приложений хватает `pnpm -r`, кеш сборки здесь не окупается.

## 2. Общий контракт в `@kanban/shared`

Enum'ы статусов и приоритетов, zod-схемы и DTO-типы описаны один раз и используются
и для валидации запросов в API, и для валидации форм на фронте. Расхождение контракта
ловится компилятором, а не в рантайме.

Пакет собирается `tsc` в CommonJS + `.d.ts`: так его без дополнительных настроек
потребляют и Nest (CommonJS), и Next.

## 3. Версии зависимостей

| Пакет      | Версия | Почему                                                                                                                                                                          |
| ---------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| NestJS     | 11.x   | Nest 12 перешёл на ESM-only. Связка Jest + ESM + декораторы требует отдельной настройки, а 11.x по-прежнему получает патчи. Переход на 12 — отдельная задача.                   |
| TypeScript | 5.9    | Nest CLI 11 собирается на 5.9; `typescript-eslint` пока поддерживает только TS < 6.1, поэтому TS 7 сломал бы линтинг.                                                           |
| TypeORM    | 1.x    | Актуальная ветка, поддерживается `@nestjs/typeorm` 11.                                                                                                                          |
| Next.js    | 16     | App Router, актуальная версия.                                                                                                                                                  |
| MUI        | 9      | Актуальная версия, есть интеграция `@mui/material-nextjs/v16-appRouter`.                                                                                                        |
| PostgreSQL | 17     | Стабильная версия, доступна на Render. Образ `postgres:17` (Debian), а не `-alpine`: в musl нет локалезависимой сортировки, и dev/test вели бы себя иначе, чем прод (см. п. 6). |
| Node.js    | 24 LTS | Зафиксирована в `.nvmrc`.                                                                                                                                                       |

## 4. Конфигурация через env с валидацией

API валидирует переменные окружения zod-схемой при старте и падает с понятной ошибкой,
а не на первом запросе к БД.

Postgres из docker compose по умолчанию публикуется на порт **5433**: 5432 часто занят
локально установленным Postgres (`DB_PORT` переопределяет).

## 5. Модель данных и миграции

- Колонки — фиксированный enum `task_status` (`NEW`, `IN_PROGRESS`, `DONE`), а не таблица:
  по ТЗ колонок ровно три. Если понадобятся настраиваемые колонки и несколько досок —
  отдельные таблицы `boards` / `columns` и миграция данных.
- Схема меняется только миграциями (`synchronize: false`). Миграции генерируются из
  entity командой `pnpm --filter @kanban/api migration:generate src/database/migrations/<Name>`
  и регистрируются явным списком в `database/migrations/index.ts` (без glob-путей —
  одинаково работает из `dist`, в ts-jest и после бандлинга).
- CLI TypeORM работает со скомпилированным `dist`, поэтому ts-node не нужен ни локально,
  ни в проде. В проде миграции применяются перед стартом: `start:prod`.
- `id` генерирует Postgres через встроенный `gen_random_uuid()` (без расширения uuid-ossp).

## 6. Порядок задач — fractional indexing

Каждая задача хранит строковый ключ `position`; колонка сортируется по нему.
При перемещении генерируется ключ строго между соседями, и **обновляется одна строка**,
а не перенумеровывается вся колонка.

- Алгоритм — [fractional indexing](https://observablehq.com/@dgreensp/implementing-fractional-indexing)
  (base-62). npm-пакет `fractional-indexing` поставляется только как ESM, что усложняет
  Jest в CommonJS-приложении, поэтому ~40 строк алгоритма реализованы в
  `modules/tasks/domain/ordering.ts` и покрыты тестами.
- Для вставки в начало/конец используется минимальный шаг, а не деление пополам:
  после 1000 добавлений в конец ключ — 33 символа (при делении пополам было бы 200).
- Колонка `position` с `COLLATE "C"`: Postgres сравнивает ключи побайтово, как JS.
  С collation по умолчанию (`en_US.UTF-8`) порядок в `ORDER BY` мог бы разойтись с ключами.
- API перемещения: `PATCH /tasks/:id/move { status, afterId }` — «поставь после задачи X»
  (`null` — в начало, без поля — в конец). Якорь задаётся id соседа, а не индексом:
  так перемещение корректно работает и на отфильтрованной доске.
- Если якорь уже удалён или перенесён в другую колонку — `409 Conflict`: клиент видел
  устаревшую доску и должен её перезагрузить.

**Ограничение:** два одновременных перемещения в одно и то же место могут получить
одинаковый ключ. Порядок при этом остаётся детерминированным (`ORDER BY position, id`),
а следующая вставка рядом ищет соседа со строго большим ключом. Для учебной доски это
приемлемо; при реальной конкурентной нагрузке — уникальный индекс `(status, position)`
и повтор при конфликте.

## 7. API

- REST, префикс `/api`, Swagger UI — `/api/docs`.
- DTO создаются из общих zod-схем (`nestjs-zod`), глобальный `ZodValidationPipe`.
- Единый формат ошибок `{ statusCode, error, message, details? }` (тип `ApiErrorBody`
  в `@kanban/shared`); `details` — ошибки по полям для 400.
- Сущности не отдаются наружу напрямую: явный маппер `toTaskDto`, чтобы новые колонки БД
  не утекали в ответы случайно.
- `GET /api/health` проверяет БД (`SELECT 1`) и отвечает 503, если она недоступна.
- Стратегия при одновременном редактировании одной задачи — last write wins
  (оптимистичная блокировка не делалась ради экономии времени).

## 8. Тесты бэка

| Уровень | Что                                                                                                                        | Запуск          |
| ------- | -------------------------------------------------------------------------------------------------------------------------- | --------------- |
| Unit    | генератор ключей порядка (таблица случаев, края, рандомизированный тест с seed, регрессия длины ключей)                    | `pnpm test`     |
| Unit    | `TasksService`: создание, редактирование, перемещения, ошибки 400/404/409, совпавшие ключи                                 | `pnpm test`     |
| E2E     | HTTP → Nest → Postgres: CRUD, перемещения, валидация, формат ошибок, контракт ответа, `COLLATE "C"`, синхронность миграций | `pnpm test:e2e` |

- Сервис тестируется на in-memory репозитории, повторяющем семантику SQL-запросов, а не на
  моках отдельных вызовов: тесты проверяют поведение и не ломаются от рефакторинга запросов.
- E2E идут на отдельной базе `kanban_test` (создаётся init-скриптом docker compose,
  в CI — `TEST_DATABASE_URL`); схема каждый раз строится реальными миграциями.
- Проверка типов тестов — в `pnpm typecheck`; ts-jest работает в режиме `isolatedModules`.

## 9. Фронтенд

**Структура (упрощённый Feature-Sliced):**

```
apps/web/src/
├─ app/            # Next App Router: layout, page, провайдеры
├─ features/       # сценарии: board (доска + drag & drop), board-filter, task-editor
├─ entities/task/  # всё про задачу: API, хуки React Query, realtime, чистая логика кэша, UI
└─ shared/         # без знания о задачах: http-клиент, QueryClient, тема, уведомления
```

Импорты идут только «вниз» (`features → entities → shared`), поэтому понятно, куда класть
новый код, и фичи не зависят друг от друга. Исключение — `BoardPage`: он играет роль
страницы и собирает фичи вместе (доска, фильтр, диалог); при росте приложения его стоит
вынести в отдельный слой `views/`.

- **Серверное состояние — TanStack Query.** Кэш — один массив задач в порядке доски;
  колонки получаются фильтрацией. Оптимистичное перемещение — перестановка в массиве
  (`applyMove`), позиционные ключи на клиенте не вычисляются: точный ключ приходит в ответе.
  При ошибке — откат к снимку и уведомление; после последнего из серии быстрых перемещений
  доска перезапрашивается для синхронизации. Удаление тоже оптимистичное.
- Повторы запросов: сетевые ошибки и 5xx — до 3 раз (бесплатный Render «просыпается»),
  4xx — никогда. Через 4 секунды загрузки показывается подсказка «Сервер просыпается».
- **Drag & drop — dnd-kit.** Логика (превью при переносе между колонками и итоговый
  `{ status, afterId }`) вынесена в чистые функции `features/board/lib/dnd.ts` и покрыта
  тестами. Сенсоры: мышь (6 px до старта — клик открывает карточку), touch (долгое нажатие,
  чтобы свайп скроллил страницу), клавиатура (пробел — взять/положить, Enter — открыть).
- **Телефон (< md):** одна колонка на экране, переключение вкладками со счётчиками;
  кнопка «+» создаёт задачу в открытой колонке; диалог — во весь экран. Перенос между
  колонками — через меню карточки «Переместить в…» (кладёт задачу наверх колонки) или
  поле «Колонка» в диалоге.
- **Формы:** react-hook-form + та же zod-схема `createTaskSchema` из `@kanban/shared`,
  что валидирует запросы на сервере. Ошибки полей из ответа API показываются у полей.
- **Состояния:** скелетон загрузки, ошибка загрузки с «Повторить», предупреждение при
  неудачном фоновом обновлении (данные остаются на экране), пустая доска с призывом
  создать задачу, пустая колонка, ошибки действий — в snackbar.
- Тема MUI следует системной (светлая/тёмная) через CSS-переменные.
- Тесты фронта (Vitest) покрывают чистую логику: модель кэша, drag & drop, фильтр.
  Компоненты проверены вручную в браузере (desktop и 375 px), автотестов UI нет —
  ограничение по времени.

## 10. Улучшения

### B. Отмена удаления вместо «Вы уверены?»

Задача исчезает сразу, в snackbar 6 секунд доступна кнопка «Отменить». Подтверждающий
диалог убран: он тормозит каждое удаление, а защищает от ошибки хуже, чем Undo.

- Мягкое удаление: колонка `deleted_at` (`@DeleteDateColumn`, отдельная миграция).
  TypeORM сам скрывает такие строки во всех запросах, включая query builder.
- `POST /api/tasks/:id/restore` возвращает задачу в ту же колонку и на то же место
  (позиция не менялась); идемпотентен. На клиенте задача вставляется по ключу позиции
  (`insertByPosition`), а не в конец.
- **Ограничение:** удалённые строки не вычищаются. Следующий шаг — периодическая очистка
  старше N дней (`@nestjs/schedule`) или partial index `WHERE deleted_at IS NULL`, если
  таблица вырастет.

### D. Поиск и фильтр по приоритету

Строка поиска (название + описание, без учёта регистра, «ё» = «е») и переключатели
приоритетов; «Найдено N из M» и «Сбросить».

- Фильтр в URL (`?q=…&priority=HIGH,LOW`): переживает перезагрузку, им можно поделиться.
  `router.replace` (не `push`), чтобы ввод не засорял историю; ввод с debounce 250 мс.
- Фильтрация на клиенте: доска загружена целиком, фильтр мгновенный и сам подхватывает
  realtime-обновления. Для больших досок — перенос на сервер (`GET /tasks?q=&priority=`,
  `ILIKE` + индекс).
- Drag & drop на отфильтрованной доске работает: якорь `afterId` — видимый сосед.

### A. Обновления в реальном времени (WebSocket)

Изменения из другой вкладки или с другого устройства появляются без перезагрузки;
в шапке — индикатор «Онлайн / Нет связи».

- Сервер: `TasksService` публикует доменные события в `TaskEvents` (RxJS `Subject`),
  `TasksGateway` (Socket.IO, тот же порт, путь `/socket.io`) рассылает их всем клиентам.
  Бизнес-логика не знает о сокетах; события отправляются только после успешной записи в БД.
  CORS для сокетов берётся из того же `CORS_ORIGIN`, что и для HTTP.
- Событие минимальное — `{ type, taskId }`; клиент в ответ перезапрашивает доску
  (с задержкой 150 мс, чтобы серия событий дала один запрос). Это проще и надёжнее,
  чем сливать частичные обновления в кэш. Пока выполняется собственная мутация, перезапрос
  откладывается, чтобы не затереть оптимистичное состояние. После переподключения доска
  перезапрашивается — события за время разрыва могли потеряться.
- Только транспорт `websocket` (без long-polling): за прокси не нужны sticky sessions.
- **Ограничения:** события получают все клиенты (нет авторизации и комнат по доскам);
  при нескольких инстансах API понадобится Redis-адаптер Socket.IO; своё же изменение
  вызывает один лишний `GET` (можно отфильтровать по id сокета, но это усложнит API).
