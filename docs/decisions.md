# Технические решения

Короткий журнал решений: что выбрали, почему и чем пожертвовали.

## 1. Монорепо на pnpm workspaces

`apps/api` (NestJS), `apps/web` (Next.js), `packages/shared` (общий контракт API).
Один `clone`, общие конфиги TypeScript/ESLint/Prettier, атомарные изменения «бэк + фронт» в одном PR.
Turborepo не используем: для двух приложений хватает `pnpm -r`, кеш сборки здесь не окупается.

## 2. Общий контракт в `@kanban/shared`

Enum'ы статусов и приоритетов, zod-схемы и DTO-типы описаны один раз и используются
и для валидации запросов в API, и для валидации форм на фронте. Расхождение контракта
ловится компилятором, а не в рантайме.

Пакет собирается `tsc` в CommonJS + `.d.ts`: так его без дополнительных настроек
потребляют и Nest (CommonJS), и Next.

## 3. Версии зависимостей

| Пакет      | Версия | Почему                                                                                                                                                        |

| NestJS     | 11.x   | Nest 12 перешёл на ESM-only. Связка Jest + ESM + декораторы требует отдельной настройки, а 11.x по-прежнему получает патчи. Переход на 12 — отдельная задача. |
| TypeScript | 5.9    | Nest CLI 11 собирается на 5.9; `typescript-eslint` пока поддерживает только TS < 6.1, поэтому TS 7 сломал бы линтинг.                                         |
| TypeORM    | 1.x    | Актуальная ветка, поддерживается `@nestjs/typeorm` 11.                                                                                                        |
| Next.js    | 16     | App Router, актуальная версия.                                                                                                                                |
| MUI        | 9      | Актуальная версия, есть интеграция `@mui/material-nextjs/v16-appRouter`.                                                                                      |
| PostgreSQL | 17     | Стабильная версия, доступна на Render.                                                                                                                        |
| Node.js    | 24 LTS | Зафиксирована в `.nvmrc`.                                                                                                                                     |

## 4. Конфигурация через env с валидацией

API валидирует переменные окружения zod-схемой при старте и падает с понятной ошибкой,
а не на первом запросе к БД.

Postgres из docker compose по умолчанию публикуется на порт **5433**: 5432 часто занят
локально установленным Postgres (`DB_PORT` переопределяет).

## 5. Модель данных и миграции

- Колонки — фиксированный enum `task_status` (`NEW`, `IN_PROGRESS`, `DONE`), а не таблица:
  по ТЗ колонок ровно три. Если понадобятся настраиваемые колонки и несколько досок —
  отдельные таблицы `boards` / `columns` и миграция данных.
- Схема меняется только миграциями (`synchronize: false`). Миграции генерируются из
  entity командой `pnpm --filter @kanban/api migration:generate src/database/migrations/<Name>`
  и регистрируются явным списком в `database/migrations/index.ts` (без glob-путей —
  одинаково работает из `dist`, в ts-jest и после бандлинга).
- CLI TypeORM работает со скомпилированным `dist`, поэтому ts-node не нужен ни локально,
  ни в проде. В проде миграции применяются перед стартом: `start:prod`.
- `id` генерирует Postgres через встроенный `gen_random_uuid()` (без расширения uuid-ossp).

## 6. Порядок задач — fractional indexing

Каждая задача хранит строковый ключ `position`; колонка сортируется по нему.
При перемещении генерируется ключ строго между соседями, и **обновляется одна строка**,
а не перенумеровывается вся колонка.

- Алгоритм — [fractional indexing](https://observablehq.com/@dgreensp/implementing-fractional-indexing)
  (base-62). npm-пакет `fractional-indexing` поставляется только как ESM, что усложняет
  Jest в CommonJS-приложении, поэтому ~40 строк алгоритма реализованы в
  `modules/tasks/domain/ordering.ts` и покрыты тестами.
- Для вставки в начало/конец используется минимальный шаг, а не деление пополам:
  после 1000 добавлений в конец ключ — 33 символа (при делении пополам было бы 200).
- Колонка `position` с `COLLATE "C"`: Postgres сравнивает ключи побайтово, как JS.
  С collation по умолчанию (`en_US.UTF-8`) порядок в `ORDER BY` мог бы разойтись с ключами.
- API перемещения: `PATCH /tasks/:id/move { status, afterId }` — «поставь после задачи X»
  (`null` — в начало, без поля — в конец). Якорь задаётся id соседа, а не индексом:
  так перемещение корректно работает и на отфильтрованной доске.
- Если якорь уже удалён или перенесён в другую колонку — `409 Conflict`: клиент видел
  устаревшую доску и должен её перезагрузить.

**Ограничение:** два одновременных перемещения в одно и то же место могут получить
одинаковый ключ. Порядок при этом остаётся детерминированным (`ORDER BY position, id`),
а следующая вставка рядом ищет соседа со строго большим ключом. Для учебной доски это
приемлемо; при реальной конкурентной нагрузке — уникальный индекс `(status, position)`
и повтор при конфликте.

## 7. API

- REST, префикс `/api`, Swagger UI — `/api/docs`.
- DTO создаются из общих zod-схем (`nestjs-zod`), глобальный `ZodValidationPipe`.
- Единый формат ошибок `{ statusCode, error, message, details? }` (тип `ApiErrorBody`
  в `@kanban/shared`); `details` — ошибки по полям для 400.
- Сущности не отдаются наружу напрямую: явный маппер `toTaskDto`, чтобы новые колонки БД
  не утекали в ответы случайно.
- `GET /api/health` проверяет БД (`SELECT 1`) и отвечает 503, если она недоступна.
- Стратегия при одновременном редактировании одной задачи — last write wins
  (оптимистичная блокировка не делалась ради экономии времени).
